## Decisions most likely to change

1. **One move standard.** Update `brain/contact-rules.md` and `contact-retention-review` so an employer-name mismatch is a review flag. `contact-move-routing` and retention take an as-of date, pinned to 2026-09-28 in tests. Contacts with no evidence row get no move classification or move action. A matched profile URL and person name are required for every non-uncertain label. Apply uncertainty guards first: missing/invalid observation or destination start date; any supplied role date after as-of; observation after as-of or more than 90 days old; origin domain unequal to the CRM company domain; active roles at different-domain employers; conflicting recent current employers; or a destination title containing `advisor`, `fractional`, or `consultant` (case-insensitive). Then `same role` means same verified domain and title; `changed role` means same verified domain, new title, and a dated start for that role; `confirmed move` means the origin work-history role has a valid end date and a different-domain destination role is active. A blank origin end date is allowed for a same-company same-role case; for a different-domain move it is uncertain. Name-only origin similarity stays uncertain. Retention owns keep, hold, and archive; `contact-move-routing` alone owns owner tasks and move-field proposals. Both use the same move rule ID. `data-accuracy-audit` still flags a name mismatch as a data discrepancy. The example proposal row that blanks P006's company from a name mismatch is an unsafe planted case.
2. **Move-event identity.** First group contact rows with the same verified profile URL and person name as one person; a shared URL with conflicting names is uncertain. The person key is that normalized profile URL. A move event key is `person key | normalized origin domain | normalized destination domain | destination role start date`; a same-company role change uses that company domain for both sides. Start date comes from work history; when absent, classification is uncertain and no task is proposed. `contact-move-routing` records the key in each output. For task deduplication it reads proposed or approved `task for owner` rows in `brain/proposals/` by event key; `brain/moves/` holds reports only and does not decide task status. An existing task suppresses another task for that event even when the observation date or topic changes. Route to `companies.csv` `owner` by `company_id`, never the contact owner field. A sidecar `move-contacts.csv` supplies two duplicate records for one person at owned C003; their contact owner differs from C003's company owner. This isolates both duplicate-task and owner-source checks without changing the wave 1/2 export.
3. **Call facts.** `brain/call-rules.md` holds stable rule IDs. Synthetic `brain/calls/call-notes.csv` holds one exact excerpt per row, each with its own rep-confirmation value and date. Each row also labels its `claim_value` as `present` or `absent`, and the quote must support that label. The skill joins each `company_id` to `brain/crm-export/companies.csv` `domain` before counting. A theme requires the same `pain_key` in confirmed `present` notes from at least two unique domains. Only C003 and C010 have qualifying `present` notes on the theme pain key. C001 and C002 use a different pain key and count as one domain for that separate pain. The mixed call at C003 has one confirmed theme-pain excerpt and one unconfirmed excerpt. Confirmed `present` and `absent` excerpts for the same pain at one company create a conflict: that company contributes no evidence for that pain until a person resolves it. C008's opposite excerpts share the C003/C010 theme pain key and one `call_id`; C003/C010 remain the qualifying pair. One file in `brain/themes/` holds fact quotes, hypotheses, gaps, and a proposed theme or `none`. `call-private` cites `draft-public-only`: private calls produce no outbound draft or published claim.
4. **Maintenance.** Task 1 creates `brain/runbook.md` with check IDs, owners, interval days, first due dates, and a required evidence type, plus `brain/maintenance/history.csv` with `check_id`, `completed_at`, and `evidence_path`. As-of date is an input, fixed to 2026-09-28 in the fixture key. A valid latest completion sets the next due date to completion date plus interval days; a never-run check uses its first due date. With no history row, missing evidence is expected and the date decides `not yet due`, `due`, or `overdue`. A completed history row is `current` before its next due date. A missing owner, invalid or future completion date, or absent/unreadable required evidence path on a claimed completion makes the result `blocked` before date classification. Before opening an evidence path, resolve it and require the resolved target beneath `brain/maintenance/evidence/`; a path resolving inside is allowed regardless of its spelling. The readable evidence file must name the same `check_id`, `evidence_type`, and `completed_at` as the runbook/history row; a readable wrong-check or wrong-type file is blocked. Plant an outside absolute path, an escaping `..` path, a symlink to a readable file outside the evidence directory, and a readable wrong-evidence file; each must be blocked. Check-level follow-ups live in the dated outcome, not a CRM proposal. A CRM task row requires a named company or contact record.
5. **CSV scope.** All four Connect sections, including the updated retention skill, select local CSV and synthetic notes for this wave regardless of installed connectors. Future live access requires a separate activation plan. New files are local evidence and proposals only. A missing CRM property or source stays a gap. A confirmed field with no mapping gets a person-facing gap, never a guessed row.
